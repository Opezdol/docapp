# docapp

Приложение отделения анестезиологии: учёт платных анестезий и распределение
выплат по бригадам. Название рабочее — «docapp» (доктора), можно сменить
в любой момент.

## Концепция

- **Врачи вводят** проведённые платные анестезии с личных телефонов:
  полное ФИО пациента и медсестру бригады. Дата подачи проставляется
  автоматически; номер истории болезни не хранится (ADR-14, минимизация).
- **Бригада** — пара «врач + медсестра». Медсестра выбирается в самой форме
  анестезии, выбор запоминается сразу (без кнопки). Каждая запись фиксирует
  ту медсестру, что выбрана в момент ввода.
- **Бухгалтерия** раз в месяц присылает Excel-файл распределения:
  ФИО пациента, дата, объём выплаты врачу, объём выплаты сестре,
  графа «кто выполнил» — пустая. ~450 строк в месяц.
- **Сопоставление** — ядро системы: строки файла автоматически связываются
  с введёнными анестезиями (по ФИО + дате), несовпавшие разбираются вручную.
  Часть введённых анестезий в файле отсутствует — это нормально.
- **Результат**: файл для бухгалтерии (пофамильное распределение:
  ФИО врача/сестры, идентификационный номер в бухгалтерии, объём выплат
  за месяц) + сводка по бригадам. Контроль: объём назначенных средств
  должен сойтись с объёмом распределённых.
- **Врач видит**: какие из его анестезий оплачены и суммарные выплаты
  по распределениям.

## Архитектурные решения (зафиксированы)

### ADR-1. Модель домена

- `Employee` — человек (врач или медсестра): фамилия, имя, отчество
  отдельными полями (нужны для приветствия «Иван Иванович» и списков),
  роль, идентификационный номер в бухгалтерии. Полное ФИО собирается
  свойством `full_name`. Однофамильцы различаются числовым id.
- `Anesthesia` — запись о проведённой анестезии: полное ФИО пациента,
  врач, медсестра (пара из формы ввода), дата подачи (проставляется
  автоматически) и таймстемп создания. Номер истории болезни не хранится
  (ADR-14). Отдельной сущности «бригада» нет — пара хранится в записи.
- `Payment` — строка из файла бухгалтерии: ФИО пациента, дата, выплата
  врачу, выплата сестре, привязка к бригаде (заполняется при разноске).

### ADR-2. Деньги — Decimal, не float

Опыт market_flow переносится: все суммы — `Decimal`, в SQLite хранятся
строкой. Никаких float для денег.

### ADR-3. Сопоставление — авто по ФИО, доводка вручную

Автоматический матчинг строк файла с анестезиями (ФИО пациента; дата
процедуры не хранится — только дата подачи, ADR-14). Несовпавшие
строки заведующий привязывает к бригаде вручную («добавить эти суммы на
нужные бригады»). Объём назначенных должен совпадать с объёмом
распределённых — контроль сумм обязателен.

### ADR-4. Медсестра — поле формы, выбор запоминается

Врач выбирает медсестру в самой форме анестезии. Выбор сохраняется сразу
по клику в поле (без кнопки) и запоминается: при следующем входе селектор
предвыбран тем же значением. Каждая запись фиксирует ту медсестру, что
выбрана в момент добавления. Отдельной сущности «бригада» нет.

### ADR-5. Роли и доступ

Врач видит только свои записи и свои выплаты, может вводить, править,
удалять. Медсестра входит в систему (логин/пароль) и видит только те
анестезии, где она указана как сестра — только просмотр, без ввода
и правки (источник записи один — врач, иначе дубли). Заведующий видит
всех, включая разноску файлов и экспорт. Пароли — только хеш.

Старшая сестра — отдельная роль `head_nurse` (ADR-11): права медсестры плюс
управление подприложением «Потребности»; к финансовой разноске и админке
«Приказов» доступа не имеет.

### ADR-6. Хранилище — SQLite, один файл

Бэкап = копия файла. Объёмы (~500–800 записей в месяц) — копейки для SQLite.

### ADR-7. Сервер — VPS в России

Больничная сеть закрыта, приложение живёт в интернете и доступно с личных
телефонов. Российский VPS: 24/7, доступ отовсюду, 152-ФЗ без вопросов
трансграничной передачи. Приложение не привязано к конкретному хостингу —
миграция возможна в любой момент.

### ADR-8. Интерфейс — PWA, стек — Python + FastAPI + SQLite

PWA (Progressive Web App) — страница, которая устанавливается на телефон
как приложение: врач один раз нажимает «Добавить на главный экран» —
и открывает её с иконки на весь экран, как обычное приложение. Обновляется
само (исправили на сервере — у всех новая версия при следующем открытии).

Почему PWA, а не нативное приложение:
- один код работает на iOS и Android (нативное = два кода или новый язык);
- не нужны App Store / Google Play, аккаунты разработчиков, модерация,
  $99/год — приложение живёт на своём VPS, доступно только по ссылке
  и логину, данные не проходят через Apple/Google;
- язык остаётся Python, который пользователь уже знает.

Бэкенд — FastAPI + SQLite (ADR-6). Серверная часть одинакова для PWA
и для нативного приложения: если когда-нибудь захотим нативное —
переписывается только интерфейс, сервер не трогаем.

### ADR-9. Подприложения: меню и заглушки

docapp — первое подприложение в общем интерфейсе. В base.html — меню
подприложений: «Анестезии», «Компендиум», «Потребности». Маршруты каждого
вынесены в отдельные APIRouter-модули.

Решение осознанное: когда появится второе реальное подприложение,
маршруты каждого выносятся в отдельные модули (APIRouter). Сейчас этого
не делаем — рефакторинг работающих маршрутов без немедленной выгоды,
правило «не переусложнять старт».

Страница «Мои данные» (/me) — просмотр своих данных (ФИО, роль, логин,
номер в бухгалтерии), без правки. Нужна, чтобы сотрудник мог проверить,
что заведующий ввёл верно. Правка появится вместе с админ-панелью (этап 3).

Меню адаптивное: на широких экранах — слева, на телефоне — строкой сверху.

### ADR-10. Подприложение «Компендиум»: LLM-wiki по курируемым статьям

На месте RAG-консультанта `/orders` (ADR-9) — подприложение «Компендиум»
(`/compendium`): вопрос-ответ по курируемой базе знаний отделения. Вместо
чанкинга PDF по 600 симв. — двухуровневая модель «источник правды + выжимка».

- **Источник правды** — загруженный PDF (приказ, инструкция, скан). Для
  сканов без текстового слоя — OCR через vision-модель (текст + таблицы).
- **Курируемые .md-статьи** — тщательно отобранные тезисы (по анестезиологии),
  связанные с источником. Версии + статус черновик/опубликовано: в ответах
  участвуют только опубликованные.
- **Поиск** — BM25 по секциям опубликованных статей (заголовок важнее тела),
  без эмбеддингов. Цитата `[1]` ведёт на статью, статья — на PDF-источник.
- **LLM и vision — RouterAI** (https://routerai.ru/api/v1): один ключ
  `AI_API_KEY`, модели ответов и OCR настраиваются env-переменными.
- **Изоляция**: код в `src/docapp/ai/` (общий ИИ-слой) и `src/docapp/wiki/`,
  данные — `data/wiki/wiki.db` (источники, статьи, ревизии, связи, диалоги).
- **Роль `editor`**: заведующий (`head`) и редактор (`editor`) курируют —
  загружают PDF и правят/публикуют статьи; настройки — только `head`.

Изменение доступа (ADR-11): медсёстры (`nurse`) к «Компендиуму» не
допускаются (403, пункт меню скрыт) — для врачей, старшей сестры,
редактора и заведующего.

### ADR-11. Подприложение «Потребности»: недельные заявки точек пополнения

Еженедельные заявки на расходку (медикаменты, растворы, расходные материалы)
от точек пополнения двух баз (Ленская, Таймырская) и результирующая потребность
для аптеки. ТЗ: `docs/ТЗ-потребности.md`.

- **Роль `head_nurse`** (старшая сестра): права медсестры плюс «Потребности»
  полностью (доска, правки, закрытие, отчёты, аналитика). Админка «Компендиума»
  ей недоступна (проверки `== HEAD`).
- **Изоляция**: пакет `src/docapp/needs/`, своя БД `data/needs/needs.db`,
  файл-каталог `data/needs/catalog.yaml` (базы, точки, группы, препараты,
  единицы — данные, не код; авто-перечитывание без рестарта). Основная БД
  не затрагивается.
- **Рабочий цикл**: календарная неделя (пн–вс), сброс в понедельник; точка
  пополнения = один запрос в неделю; статусы черновик/отправлено; закрытие по
  базе → отчёт .xlsx (два листа: «Растворы» — по точкам + итог; «Потребность» —
  остальное суммарно по группам); переоткрытие = снятие закрытия и пересборка
  отчёта.
- **Снимки**: строки запросов хранят название, единицу и группу на момент запроса —
  правка каталога не ломает историю.
- **Изменения доступа**: медсёстры лишены доступа к «Компендиуму» (403,
  изменение ADR-10); врачам недоступны «Потребности»; заведующий видит всё,
  включая «Потребности».

### ADR-14. Минимизация персональных данных (152-ФЗ)

Сознательный отказ от хранения лишнего: номер истории болезни не хранится
вовсе (миграция схемы v2 стирает и колонку, и старые значения), дата
процедуры заменена датой подачи сведений. Шифрование самой SQLite-БД
сознательно не применяется: при ключе на том же сервере оно защищает только
от кражи диска/бэкапа, но не от уязвимостей самого приложения, а SQLCipher
на shared-хостинге непропорционально сложен. Риск снижается минимизацией
данных, контролем доступа по ролям и HTTPS-only, а не шифрованием файла.

## Точки расширения (осознанные, проектируем под них, но не строим)

1. **Формы файлов бухгалтерии** — пользователь предоставит точные формы
   при разработке модуля экспорта (этап 2). Модель Employee уже содержит
   идентификационный номер — заложено.
2. **Фото расчётного листа** — распознавание данных (ФИО, номер и/б)
   и автоматическое заполнение формы + сверка. OCR на Python.
3. **База внутренних документов** отделения + **круглосуточный консультант**
   (вопрос-ответ по базе). Отдельный модуль поверх той же БД.
4. **Контроль сумм** — расхождение «назначено vs распределено» видно
   в интерфейсе.

## Структура

```
src/docapp/
  domain/          # Employee, Anesthesia, Payment — без зависимостей
  storage/         # порты (ABC) + Sqlite*Store (employees, anesthesia, active_nurse)
  auth/            # хеши паролей (pbkdf2), вход, активная сестра
  records/         # AnesthesiaService: ввод, «мои записи», правка, удаление
  allocation/      # импорт Excel, матчинг, разноска, экспорт, сводки
  ai/              # общий слой вызовов ИИ (LLM, vision-OCR)
  wiki/            # «Компендиум»: PDF-источники + курируемые .md-статьи + QA
  needs/           # потребности: заявки точек, отчёты, аналитика
  web/             # FastAPI + PWA-интерфейс (мобильный)
tests/             # pytest
main.py            # запуск
README.md          # этот файл
```

2. ⏳ Этап 2 (ядро): импорт Excel, автосопоставление, разноска, экспорт —

## Запуск

```bash
uv run pytest -q          # тесты (280 шт.)
uv run python main.py     # сервер на http://127.0.0.1:8000 (за reverse-proxy)
# для доступа с телефона по локальной сети при разработке:
DOCAPP_HOST=0.0.0.0 uv run python main.py
```

Версия сборки: рядом с брендом «docapp» в шапке показывается короткий хэш
последнего коммита. Источники по приоритету: env `DOCAPP_GIT_REVISION`,
файл `REVISION` в корне (записывается `scripts/update.sh` при rsync-деплое),
иначе `git rev-parse --short HEAD` (в разработке/на сервере с `.git`).

Настройки: путь к БД — переменная окружения DOCAPP_DB (по умолчанию
data/docapp.db), секрет сессий — data/secret.key (создаётся сам при
первом запуске). Полный список переменных — в `.env.example` (скопируйте
его в `.env` на сервере).

Создание сотрудников (до админ-панели в этапе 3):

```bash
# заведующий (входит в систему)
uv run python -m docapp.cli user Петров Пётр Иванович --role head --login petrov --password secret
# врач (пароль сгенерируется сам и напечатается один раз)
uv run python -m docapp.cli user Иванов Иван Иванович --role doctor --login ivanov
# медсестра без логина (не будет заходить в систему)
uv run python -m docapp.cli nurse Сидорова Анна Петровна
# медсестра с логином (сможет смотреть свои анестезии, пароль сгенерируется)
uv run python -m docapp.cli nurse Козлова Мария --login masha
# старшая сестра (роль head_nurse — полные права в «Потребностях»)
uv run python -m docapp.cli user Петрова Елена Ивановна --role head_nurse --login elena --password secret
# номер из бухгалтерии (можно сразу или позже, когда бухгалтерия пришлёт)
uv run python -m docapp.cli buh-id 1 B-1042
```

## Запуск на сервере (VPS)

Приложение живёт на VPS за TLS (ADR-7). HTTPS терминирует обратный прокси,
uvicorn слушает 127.0.0.1:8000.

**TLS-терминатор — Caddy** (авто-TLS, сертификаты Let's Encrypt сами):

```caddyfile
docapp.example.ru {
    reverse_proxy 127.0.0.1:8000
}
```

Или **nginx** — server block с ssl-сертификатом и `proxy_pass http://127.0.0.1:8000;`
(плюс обычные для FastAPI заголовки: `X-Forwarded-Proto https` и т.п.).

> **`.env`**: полный список переменных окружения и шаблон — в `.env.example`.
> Скопируйте его в `.env` в корне проекта (`cp .env.example .env`) и заполните
> (`AI_API_KEY`, `DOCAPP_HTTPS_ONLY=1` и т.д.) — systemd-юнит ниже читает
> именно этот файл.

**systemd-юнит** (`/etc/systemd/system/docapp.service`):

```ini
[Unit]
Description=docapp
After=network.target

[Service]
User=docapp
WorkingDirectory=/путь/к/docapp
EnvironmentFile=/путь/к/docapp/.env
ExecStart=/usr/bin/uv run --directory /путь/к/docapp python main.py
Restart=always

[Install]
WantedBy=multi-user.target
```

> **ВАЖНО**: при работе за TLS выставить `DOCAPP_HTTPS_ONLY=1` в `.env` —
> куки сессий получат атрибут Secure и будут передаваться только по HTTPS.

**Бэкап** (ADR-6: БД — один файл, бэкап — копия). Ежедневно в 3:00 через cron:

```cron
0 3 * * * cd /путь/к/docapp && ./scripts/backup.sh >> logs/backup.log 2>&1
```

`scripts/backup.sh` снимает консистентную копию `data/docapp.db`,
`data/wiki/wiki.db`, `data/needs/needs.db` и каталога
`data/needs/catalog.yaml` в `backups/` (sqlite `.backup`, безопасен при WAL);
хранятся 14 дней, старые удаляются автоматически.

## Запуск на shared-хостинге reg.ru (Phusion Passenger)

На виртуальном хостинге reg.ru (панель ISPmanager) нет root и systemd,
а фоновые nohup-процессы хостинг убивает через ~30 секунд. Рабочий способ —
**Phusion Passenger** (панель включает его при выборе «Версия Python» в
настройках сайта). Проверено на `https://phhmn.ru`.

### Схема

```
~/data/www/ДОМЕН/            ← корень сайта (DocumentRoot)
├── passenger_wsgi.py        ← точка входа Passenger
└── venv/                    ← виртуальное окружение Python (в корне сайта!)
~/data/docapp/               ← код приложения (вне корня сайта)
```

Панель генерирует для сайта:

```
PassengerEnabled On
PassengerAppRoot ~/data/www/ДОМЕН
PassengerStartupFile passenger_wsgi.py
PassengerPython /opt/python/python-3.12/bin/python   ← системный python
```

### Подготовка (по SSH)

```bash
# 1. venv в корне сайта (именно так ожидает Passenger)
/opt/python/python-3.12/bin/python -m venv ~/data/www/ДОМЕН/venv

# 2. зависимости
~/data/www/ДОМЕН/venv/bin/pip install -e ~/data/docapp
~/data/www/ДОМЕН/venv/bin/pip install a2wsgi

# 3. passenger_wsgi.py — из репозитория (см. файл): он сам
#    - ограничивает потоки numpy (OPENBLAS_NUM_THREADS=1) ДО импорта,
#      иначе numpy зависает под Passenger;
#    - добавляет site-packages venv в sys.path (PassengerPython — системный);
#    - грузит .env из каталога приложения;
#    - оборачивает FastAPI в WSGI через a2wsgi.ASGIMiddleware
#      (НЕ WSGIMiddleware — это не тот класс!)
```

### Ключевые грабли (найдены эмпирически)

1. **`a2wsgi.WSGIMiddleware` — не тот класс.** Нужен `a2wsgi.ASGIMiddleware`
   (конвертит ASGI→WSGI). `WSGIMiddleware` даёт 502 «Incomplete response».
2. **`import numpy` зависает под Passenger** (OpenBLAS создаёт пул потоков).
   Обязательно `OPENBLAS_NUM_THREADS=1` + `OMP_NUM_THREADS=1` в самом начале
   `passenger_wsgi.py`, до импорта numpy.
3. **venv — в корне сайта** (`~/data/www/ДОМЕН/venv`), не в `~/data/docapp`.
4. **os.execl на venv-python НЕ нужен** — Passenger запускает системным
   python, а site-packages venv добавляется в sys.path (иначе 502).
5. После замены `passenger_wsgi.py` убить старый wsgi-loader:
   `pkill -f "u3617050.*wsgi-loader"` — Passenger перезапустит с новым кодом.

Полезные ссылки: [инструкция reg.ru по Flask](https://help.reg.ru/support/hosting/php-asp-net-i-skripty/kak-ustanovit-flask-na-hosting),
[рабочий пример FastAPI на reg.ru](https://github.com/devlumba/fastapi-tracking-time-1).

### Обновление на сервере (`scripts/update.sh`)

Полный цикл обновления (запускать с локальной машины из корня docapp):

```bash
./scripts/update.sh
```

Скрипт делает по порядку:

1. **Бэкап БД** на сервере (`scripts/backup.sh` — docapp/wiki/needs).
2. **rsync кода** на сервер (исключая `.venv`, `data`, `.env`).
3. **Обновление зависимостей** в обоих venv (приложения и Passenger-корня сайта).
4. **Миграции схемы БД**: `docapp migrate` — применяет миграции ко всем трём
   БД (docapp/wiki/needs), создаёт их при отсутствии. Идемпотентно.
5. **Перезапуск Passenger**: убивает `wsgi-loader` — Passenger подхватывает
   новый код при следующем запросе.
6. **Проверка HTTPS** домена.

### Миграции схемы БД

Версия схемы хранится в `PRAGMA user_version` каждой БД. Текущая версия —
`SCHEMA_VERSION` в `src/docapp/storage/sqlite_store.py`,
`src/docapp/wiki/store.py`, `src/docapp/needs/store.py`.

**Как добавить миграцию** (при изменении схемы):

1. Увеличьте `SCHEMA_VERSION` на 1.
2. Добавьте кортеж в список `_MIGRATIONS` соответствующего хранилища:
   ```python
   _MIGRATIONS = [
       # (2, "добавить колонку X", [
       #     "ALTER TABLE employees ADD COLUMN x TEXT NOT NULL DEFAULT ''",
       # ]),
   ]
   ```
3. Примените на сервере: `./scripts/update.sh` (или `docapp migrate`).

> **ВАЖНО**: не редактируйте уже опубликованные миграции — добавляйте новые.
> Миграции применяются по порядку при подключении к БД, так что ручной
> запуск `docapp migrate` нужен только чтобы не ждать первого запроса.

## Компендиум (подприложение «База знаний»)

Вопрос-ответ по курируемой базе знаний отделения (ADR-10). Заведующий/редактор
загружают PDF-источник (приказ, инструкция, скан — распознаётся через vision)
и составляют `.md`-статью с тезисами по анестезиологии, привязанную к источнику.
Консультант отвечает по опубликованным статьям и цитирует их: `[1]` ведёт на
статью, статья — на PDF-источник правды.

История диалогов хранится в БД и восстанавливается при открытии страницы;
для заведующего есть страница «Вопросы» — что спрашивают сотрудники и расход
токенов.

### Роли

- **Врачи, старшая сестра, заведующий** — задают вопросы, читают статьи/источники.
- **Заведующий (`head`) и редактор (`editor`)** — загружают PDF, правят/публикуют
  статьи, удаляют источники.
- **Заведующий (`head`)** — настройки (промпт, top_k, температура, история).
- Медсёстрам (`nurse`) доступ закрыт (403, пункт меню скрыт).

### Модель данных

- `sources` — источник правды (PDF + OCR-текст + таблицы), неизменяем после OCR.
- `articles` — статья (draft/published/archived) + `published_revision_id`.
- `revisions` — версии .md (откат, публикация конкретной ревизии).
- `article_links` — связь статья → источник (с якорем «стр. N, п. M»).
- `messages` — история QA + учёт токенов; `settings` — настройки.

### Как это работает

1. `head`/`editor` загружают PDF во вкладке «Источники» → фоновый OCR
   (если скан — vision-модель; текст + таблицы) → статус в БД.
2. `head`/`editor` пишут `.md` во вкладке «Статьи», привязывают источник,
   сохраняют черновик, затем публикуют.
3. Вопрос → BM25 по секциям опубликованных статей (заголовок важнее тела) →
   топ-N секций в контекст LLM → стриминг ответа с цитатами.

### Настройки консультанта (только заведующий)

Вкладка «Настройки» (роль `head`) — системный промпт и параметры ответа:
`system_prompt`, `top_k` (разделов в контексте, 1–20), `temperature` (0–1),
`history_messages` (0–20). Значения вне диапазона игнорируются — применяется
дефолт.

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `AI_API_KEY` | ключ RouterAI (обязателен) | — |
| `AI_BASE_URL` | базовый URL API RouterAI | `https://routerai.ru/api/v1` |
| `AI_LLM_MODEL` | модель ответов | `openai/gpt-5.4-mini` |

## Потребности (подприложение для старшей сестры)

Еженедельные заявки на расходку от точек пополнения двух баз (Ленская, Таймырская)
и результирующая потребность для аптеки. Роли: медсёстры составляют заявки,
старшая сестра (`head_nurse`) закрывает базы и генерирует отчёты, заведующий видит
всё. ТЗ: `docs/ТЗ-потребности.md`.

Интерфейс выбора точки пополнения — сеткой карточек по базам (как доска старшей):
медсестра видит сетку точек обеих баз и кликом открывает заявку выбранной точки;
старшая сестра/заведующий работают через доску (карточки точек со статусами
и авторами). Отдельного выпадающего списка «Точка пополнения» больше нет.

Для старшей сестры/заведующего отчёты доступны прямо с доски: под каждой базой —
кнопки «Отчёт (xlsx)» и «Отчёт (просмотр)», которые строят отчёт строго по этой
базе за текущую неделю. Форма «Заявка на неделю» у них скрыта и появляется при
клике на точку доски (для правки заявки). Аналитика — по кнопке «Аналитика»
в шапке доски (отдельная страница `/needs/analytics`).

Данные: `data/needs/needs.db` (заявки, история, закрытия) и `data/needs/catalog.yaml`
(базы, точки, группы, препараты, единицы — правится файлом, сервер подхватывает
изменения без рестарта).

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `NEEDS_DB` | файл БД заявок «Потребностей» | `data/needs/needs.db` |
| `NEEDS_CATALOG` | файл-каталог (базы, точки, группы, препараты) | `data/needs/catalog.yaml` |

Создание старшей сестры (роль `head_nurse`, полные права в «Потребностях»):

```bash

```
