# docapp

Приложение отделения анестезиологии: учёт платных анестезий и распределение
выплат по бригадам. Название рабочее — «docapp» (доктора), можно сменить
в любой момент.

## Концепция

- **Врачи вводят** проведённые платные анестезии с личных телефонов:
  полное ФИО пациента, номер истории болезни, бригада, дата.
- **Бригада** — пара «врач + медсестра». У врача есть «активная сестра»
  (переключается в один тап в шапке формы), анестезия фиксирует ту пару,
  которая была активна в момент ввода. Ушёл к другой сестре — переключил,
  вводит дальше; вернулся — переключил обратно.
- **Бухгалтерия** раз в месяц присылает Excel-файл распределения:
  ФИО пациента, дата, объём выплаты врачу, объём выплаты сестре,
  графа «кто выполнил» — пустая. ~450 строк в месяц.
- **Сопоставление** — ядро системы: строки файла автоматически связываются
  с введёнными анестезиями (по ФИО + дате), несовпавшие разбираются вручную.
  Часть введённых анестезий в файле отсутствует — это нормально.
- **Результат**: файл для бухгалтерии (пофамильное распределение:
  ФИО врача/сестры, идентификационный номер в бухгалтерии, объём выплат
  за месяц) + сводка по бригадам. Контроль: объём назначенных средств
  должен сойтись с объёмом распределённых.
- **Врач видит**: какие из его анестезий оплачены и суммарные выплаты
  по распределениям.

## Архитектурные решения (зафиксированы)

### ADR-1. Модель домена

- `Employee` — человек (врач или медсестра): фамилия, имя, отчество
  отдельными полями (нужны для приветствия «Иван Иванович» и списков),
  роль, идентификационный номер в бухгалтерии. Полное ФИО собирается
  свойством `full_name`. Однофамильцы различаются числовым id.
- `Anesthesia` — запись о проведённой анестезии: дата, полное ФИО пациента,
  номер истории болезни, врач, медсестра (пара, активная в момент ввода),
  таймстемп создания. Отдельной сущности «бригада» нет — пара хранится
  в записи.
- `Payment` — строка из файла бухгалтерии: ФИО пациента, дата, выплата
  врачу, выплата сестре, привязка к бригаде (заполняется при разноске).

### ADR-2. Деньги — Decimal, не float

Опыт market_flow переносится: все суммы — `Decimal`, в SQLite хранятся
строкой. Никаких float для денег.

### ADR-3. Сопоставление — авто по ФИО+дата, доводка вручную

Автоматический матчинг строк файла с анестезиями (ФИО + дата). Несовпавшие
строки заведующий привязывает к бригаде вручную («добавить эти суммы на
нужные бригады»). Объём назначенных должен совпадать с объёмом
распределённых — контроль сумм обязателен.

### ADR-4. Активная сестра — состояние врача, не справочник

Имя врача известно из логина. У врача есть «активная сестра» — быстрый
переключатель в шапке формы: выбрал сестру → вводит анестезии → переключил
другую → вводит дальше. Каждая запись фиксирует пару, активную в момент
ввода. Система помнит последний выбор врача (при следующем входе сестра
та же). Отдельной сущности «бригада» нет.

### ADR-5. Роли и доступ

Врач видит только свои записи и свои выплаты, может вводить, править,
удалять. Медсестра входит в систему (логин/пароль) и видит только те
анестезии, где она указана как сестра — только просмотр, без ввода
и правки (источник записи один — врач, иначе дубли). Заведующий видит
всех, включая разноску файлов и экспорт. Пароли — только хеш.

Старшая сестра — отдельная роль `head_nurse` (ADR-11): права медсестры плюс
управление подприложением «Потребности»; к финансовой разноске и админке
«Приказов» доступа не имеет.

### ADR-6. Хранилище — SQLite, один файл

Бэкап = копия файла. Объёмы (~500–800 записей в месяц) — копейки для SQLite.

### ADR-7. Сервер — VPS в России

Больничная сеть закрыта, приложение живёт в интернете и доступно с личных
телефонов. Российский VPS: 24/7, доступ отовсюду, 152-ФЗ без вопросов
трансграничной передачи. Приложение не привязано к конкретному хостингу —
миграция возможна в любой момент.

### ADR-8. Интерфейс — PWA, стек — Python + FastAPI + SQLite

PWA (Progressive Web App) — страница, которая устанавливается на телефон
как приложение: врач один раз нажимает «Добавить на главный экран» —
и открывает её с иконки на весь экран, как обычное приложение. Обновляется
само (исправили на сервере — у всех новая версия при следующем открытии).

Почему PWA, а не нативное приложение:
- один код работает на iOS и Android (нативное = два кода или новый язык);
- не нужны App Store / Google Play, аккаунты разработчиков, модерация,
  $99/год — приложение живёт на своём VPS, доступно только по ссылке
  и логину, данные не проходят через Apple/Google;
- язык остаётся Python, который пользователь уже знает.

Бэкенд — FastAPI + SQLite (ADR-6). Серверная часть одинакова для PWA
и для нативного приложения: если когда-нибудь захотим нативное —
переписывается только интерфейс, сервер не трогаем.

### ADR-9. Подприложения: меню и заглушки

docapp — первое подприложение в общем интерфейсе. В base.html — меню
подприложений: «Анестезии» (текущее), «Приказы» (заглушка «в разработке»).
Заглушка — просто страница, без логики.

Решение осознанное: когда появится второе реальное подприложение,
маршруты каждого выносятся в отдельные модули (APIRouter). Сейчас этого
не делаем — рефакторинг работающих маршрутов без немедленной выгоды,
правило «не переусложнять старт».

Страница «Мои данные» (/me) — просмотр своих данных (ФИО, роль, логин,
номер в бухгалтерии), без правки. Нужна, чтобы сотрудник мог проверить,
что заведующий ввёл верно. Правка появится вместе с админ-панелью (этап 3).

Меню адаптивное: на широких экранах — слева, на телефоне — строкой сверху.

### ADR-10. Подприложение «Приказы»: ИИ-консультант по внутренним приказам

На месте заглушки `/orders` (ADR-9) — реальное подприложение: вопрос-ответ
по базе внутренних приказов отделения, с цитатами «Приказ №X, раздел Y».

- **LLM и эмбеддинги — RouterAI** (https://routerai.ru/api/v1): единый
  OpenAI-совместимый API, оплата в рублях, один ключ. Никаких локальных
  моделей на сервере.
- **Полная изоляция**: новый код — в пакете `src/docapp/consult/`, свои
  данные — `data/consult/consult.db` (документы, чанки, эмбеддинги,
  история диалогов, токены). Основная БД не затрагивается.
- **Индексация офлайн** (CLI на машине заведующего): приказы → фрагменты →
  эмбеддинги RouterAI → готовый `consult.db`, который загружается на сервер.
  Сервер только ищет (numpy cosine + BM25) и отвечает (HTTP) — без
  ML-зависимостей.
- **История диалогов и учёт токенов** хранятся в БД; заведующий видит,
  что спрашивают сотрудники и сколько токенов тратится.
- Загрузка/переиндексация — только заведующий.
- ТЗ: `docs/ТЗ-консультант.md`.

Изменение доступа (ADR-11): обычные медсёстры (`nurse`) к «Приказам» не
допускаются (403 на маршрутах, пункт меню скрыт) — консультант для врачей,
старшей сестры и заведующего.

### ADR-11. Подприложение «Потребности»: недельные заявки точек пополнения

Еженедельные заявки на расходку (медикаменты, растворы, расходные материалы)
от точек пополнения двух баз (Ленская, Таймырская) и результирующая потребность
для аптеки. ТЗ: `docs/ТЗ-потребности.md`.

- **Роль `head_nurse`** (старшая сестра): права медсестры плюс «Потребности»
  полностью (доска, правки, закрытие, отчёты, аналитика). Админка «Приказов»
  ей недоступна (проверки `== HEAD`).
- **Изоляция**: пакет `src/docapp/needs/`, своя БД `data/needs/needs.db`,
  файл-каталог `data/needs/catalog.yaml` (базы, точки, группы, препараты,
  единицы — данные, не код; авто-перечитывание без рестарта). Основная БД
  не затрагивается.
- **Рабочий цикл**: календарная неделя (пн–вс), сброс в понедельник; точка
  пополнения = один запрос в неделю; статусы черновик/отправлено; закрытие по
  базе → отчёт .xlsx (два листа: «Растворы» — по точкам + итог; «Потребность» —
  остальное суммарно по группам); переоткрытие = снятие закрытия и пересборка
  отчёта.
- **Снимки**: строки запросов хранят название, единицу и группу на момент запроса —
  правка каталога не ломает историю.
- **Изменения доступа**: медсёстры лишены доступа к «Приказам» (403, изменение
  ADR-10); врачам недоступны «Потребности»; заведующий видит всё, включая
  «Потребности».

## Точки расширения (осознанные, проектируем под них, но не строим)

1. **Формы файлов бухгалтерии** — пользователь предоставит точные формы
   при разработке модуля экспорта (этап 2). Модель Employee уже содержит
   идентификационный номер — заложено.
2. **Фото расчётного листа** — распознавание данных (ФИО, номер и/б)
   и автоматическое заполнение формы + сверка. OCR на Python.
3. **База внутренних документов** отделения + **круглосуточный консультант**
   (вопрос-ответ по базе). Отдельный модуль поверх той же БД.
4. **Контроль сумм** — расхождение «назначено vs распределено» видно
   в интерфейсе.

## Структура

```
src/docapp/
  domain/          # Employee, Anesthesia, Payment — без зависимостей
  storage/         # порты (ABC) + Sqlite*Store (employees, anesthesia, active_nurse)
  auth/            # хеши паролей (pbkdf2), вход, активная сестра
  records/         # AnesthesiaService: ввод, «мои записи», правка, удаление
  allocation/      # импорт Excel, матчинг, разноска, экспорт, сводки
  consult/         # консультант по приказам (T1-T11)
  needs/           # потребности: заявки точек, отчёты, аналитика
  web/             # FastAPI + PWA-интерфейс (мобильный)
tests/             # pytest
main.py            # запуск
README.md          # этот файл
```

## Дорожная карта

1. ✅ Этап 1 (MVP): домен, авторизация, форма ввода (врач + активная
   сестра), «мои записи» с правкой, PWA-интерфейс
2. ⏳ Этап 2 (ядро): импорт Excel, автосопоставление, разноска, экспорт —
   НЕ реализовано, запланирован отдельным циклом после запуска MVP+консультанта;
   остальное: экспорт файла бухгалтерии + сводки по бригадам, контроль сумм,
   статусы оплат для врачей
3. Этап 3: роли и права, админ-панель (правка «моих данных»,
   управление сотрудниками), бэкапы, полировка интерфейса
4. Этап 4: фото расчётного листа → распознавание + сверка
5. Этап 5: база документов + консультант — консультант реализован (T1-T11),
   осталось: ключ RouterAI в .env, сборка индекса реальных приказов, приёмка
   на контрольных вопросах; OCR для сканов — фаза 2
6. ⏳ Потребности (подприложение для старшей сестры) — ТЗ `docs/ТЗ-потребности.md`,
   реализация запланирована

## Запуск

```bash
uv run pytest -q          # тесты (329 шт.)
uv run python main.py     # сервер на http://0.0.0.0:8000
```

Настройки: путь к БД — переменная окружения DOCAPP_DB (по умолчанию
data/docapp.db), секрет сессий — data/secret.key (создаётся сам при
первом запуске).

Создание сотрудников (до админ-панели в этапе 3):

```bash
# заведующий (входит в систему)
uv run python -m docapp.cli user Петров Пётр Иванович --role head --login petrov --password secret
# врач (пароль сгенерируется сам и напечатается один раз)
uv run python -m docapp.cli user Иванов Иван Иванович --role doctor --login ivanov
# медсестра без логина (не будет заходить в систему)
uv run python -m docapp.cli nurse Сидорова Анна Петровна
# медсестра с логином (сможет смотреть свои анестезии, пароль сгенерируется)
uv run python -m docapp.cli nurse Козлова Мария --login masha
# старшая сестра (роль head_nurse — полные права в «Потребностях»)
uv run python -m docapp.cli user Петрова Елена Ивановна --role head_nurse --login elena --password secret
# номер из бухгалтерии (можно сразу или позже, когда бухгалтерия пришлёт)
uv run python -m docapp.cli buh-id 1 B-1042
```

## Запуск на сервере (VPS)

Приложение живёт на VPS за TLS (ADR-7). HTTPS терминирует обратный прокси,
uvicorn слушает 127.0.0.1:8000.

**TLS-терминатор — Caddy** (авто-TLS, сертификаты Let's Encrypt сами):

```caddyfile
docapp.example.ru {
    reverse_proxy 127.0.0.1:8000
}
```

Или **nginx** — server block с ssl-сертификатом и `proxy_pass http://127.0.0.1:8000;`
(плюс обычные для FastAPI заголовки: `X-Forwarded-Proto https` и т.п.).

**systemd-юнит** (`/etc/systemd/system/docapp.service`):

```ini
[Unit]
Description=docapp
After=network.target

[Service]
User=docapp
WorkingDirectory=/путь/к/docapp
EnvironmentFile=/путь/к/docapp/.env
ExecStart=/usr/bin/uv run --directory /путь/к/docapp python main.py
Restart=always

[Install]
WantedBy=multi-user.target
```

> **ВАЖНО**: при работе за TLS выставить `DOCAPP_HTTPS_ONLY=1` в `.env` —
> куки сессий получат атрибут Secure и будут передаваться только по HTTPS.

**Бэкап** (ADR-6: БД — один файл, бэкап — копия). Ежедневно в 3:00 через cron:

```cron
0 3 * * * cd /путь/к/docapp && ./scripts/backup.sh >> logs/backup.log 2>&1
```

`scripts/backup.sh` снимает консистентную копию `data/docapp.db` и
`data/consult/consult.db` в `backups/` (sqlite `.backup`, безопасен при WAL);
хранятся 14 дней, старые удаляются автоматически.

## Консультант по приказам (подприложение «Приказы»)

Вопрос-ответ по внутренним приказам отделения (ADR-10): сотрудник задаёт
вопрос на странице «Приказы», консультант отвечает по базе приказов
с цитатами «Приказ №X · раздел Y» (фрагмент раскрывается по клику).
История диалогов хранится в БД и восстанавливается при открытии страницы;
для заведующего есть страница «Вопросы» — что спрашивают сотрудники
и расход токенов. ТЗ: `docs/ТЗ-консультант.md`.

Все сотрудники видят список приказов во вкладке «Документы»: «Читать» —
полный текст, «Скачать» — оригинальный файл (.docx/.pdf сохраняется
в индекс при сборке).

### Как добавить приказ (основной путь — через веб)

Заведующий открывает «Приказы» → вкладка «Документы» → загружает .docx/.pdf.
Сервер сохраняет файлы в статичную папку приказов (`CONSULT_DOCS_DIR`)
и сам пересоберёт индекс (эмбеддинги через RouterAI, `CONSULT_API_KEY`) —
новые приказы сразу доступны для вопросов, чтения и скачивания. Пока идёт
пересборка, страница показывает индикатор; статус доступен и через
`GET /orders/status`. **История диалогов и учёт токенов сохраняются при
переиндексации** (сообщения мигрируют в новый файл индекса).

### Альтернатива: офлайн-CLI и scp (большие первичные загрузки)

Для большой первичной загрузки сборку можно выполнить офлайн от сервера —
на любой машине с доступом к RouterAI (эмбеддинги). Положите .docx/.pdf
приказы в папку `data/consult/documents/` (или `CONSULT_DOCS_DIR`) и выполните:

```bash
export CONSULT_API_KEY=<ключ RouterAI>
export CONSULT_EMBED_MODEL=text-embedding-3-small   # модель эмбеддингов RouterAI
uv run python -m docapp.consult
```

CLI возьмёт статичную папку по умолчанию. После обновления папки повторите
команду — индекс пересоберётся полностью.

Результат: `data/consult/consult.db` — документы, фрагменты и эмбеддинги
(файл переносится между машинами). На сервере: скопируйте файлы приказов
(scp) в папку приказов сервера (`CONSULT_DOCS_DIR`) и нажмите
«Перезагрузить индекс» во вкладке «Документы» (кнопка только у заведующего) —
сервер пересоберёт индекс из папки.

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `CONSULT_API_KEY` | ключ RouterAI (обязателен) | — |
| `CONSULT_BASE_URL` | базовый URL API RouterAI | `https://routerai.ru/api/v1` |
| `CONSULT_LLM_MODEL` | модель ответов | `gpt-4o-mini` |
| `CONSULT_EMBED_MODEL` | модель эмбеддингов | `text-embedding-3-small` |
| `CONSULT_INDEX_DIR` | каталог индекса | `data/consult` |
| `CONSULT_DOCS_DIR` | папка приказов | `data/consult/documents` |

Примечание: сканы PDF без текстового слоя не индексируются (нужен OCR —
фаза 2).

## Потребности (подприложение для старшей сестры)

Еженедельные заявки на расходку от точек пополнения двух баз (Ленская, Таймырская)
и результирующая потребность для аптеки. Роли: медсёстры составляют заявки,
старшая сестра (`head_nurse`) закрывает базы и генерирует отчёты, заведующий видит
всё. ТЗ: `docs/ТЗ-потребности.md`.

Данные: `data/needs/needs.db` (заявки, история, закрытия) и `data/needs/catalog.yaml`
(базы, точки, группы, препараты, единицы — правится файлом, сервер подхватывает
изменения без рестарта).

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `NEEDS_DB` | файл БД заявок «Потребностей» | `data/needs/needs.db` |
| `NEEDS_CATALOG` | файл-каталог (базы, точки, группы, препараты) | `data/needs/catalog.yaml` |

Создание старшей сестры (роль `head_nurse`, полные права в «Потребностях»):

```bash
uv run python -m docapp.cli user Петрова Елена Ивановна --role head_nurse --login elena --password secret
```
