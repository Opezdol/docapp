# ТЗ v1.0: Каркас docapp — модули, одна БД, доступ, период и статусы

Статус: **ожидает согласования владельцем**. Обсуждение — 11.09.2026.
Словарь терминов — `docs/глоссарий.md`. Решения — `docs/adr/0016…0023`.
Протокол обсуждения (вне git) — `.hermes/plans/каркас-решения.md`.

---

## 1. Цель

Убрать то, что мешает добавлять разделы и менять функциональность:

1. **Новый раздел перестаёт быть правкой шести файлов.** Сегодня добавление модуля —
   это конец `create_app`, конфиг, `cli.py`, `base.html`, `backup.sh` и список в
   документации. Цель — один файл модуля плюс строка в реестре.
2. **Схема БД меняется в одном месте.** Сегодня `_connect` и `_apply_migrations`
   дословно повторены в четырёх хранилищах, а `docapp migrate` обходит их цепочкой
   `if name == …`.
3. **Данные разделов — в одной БД с работающими внешними ключами.** Сегодня четыре
   файла и голые `*_id` на сотрудников без FK.
4. **Права задаются таблицей, а не четырьмя наборами проверок.**
5. **Период и статусы (`draft → sent → closed`) — один механизм вместо трёх копий.**
6. **Проверка каркаса — реальным модулем**, а не гипотезой: раздел «Распределение»
   (на старте — «Сводка»), у которого нет своей таблицы.

**Что НЕ меняется:** стек (Python 3.11, FastAPI, SQLite, Jinja2, vanilla JS/PWA, `uv`,
без CDN); роли и их права (решение Q10 — сохраняем фактическое поведение); поведение
существующих разделов; домен и минимизация ПДн (ADR-14); сервер и выкладка (решение Q6).

## 4. Контракт модуля (`core/registry.py`)

Модуль объявляет о себе ровно то, что нужно каркасу:

```python
@dataclass(frozen=True)
class Module:
    name: str                                   # имя модуля, оно же ключ в schema_migrations
    schema: Schema | None = None                # свои таблицы (None — своих нет)
    db_path: Callable[[], Path] | None = None   # где лежит БД модуля
    build: Callable[[], object] | None = None   # собирает контейнер модуля
    router: APIRouter | None = None             # HTTP-адаптер (None — модуль без HTTP)

MODULES = (CORE, COMPENDIUM, NEEDS, DUTY)       # docapp/modules.py: строка на модуль
```

- `MODULES` — реестр; `create_app(config, modules=MODULES)`.
- **Своя схема не обязательна.** `distribution` не имеет таблиц вовсе; модуль, которому
  нужны данные соседа, получает интерфейс соседа из общего контейнера.
- Контейнер модуля — `dataclass(frozen=True)` в `<модуль>/container.py`, собирается
  функцией `build()`. Доступ в роутере — `registry.container_of(request, "needs",
  NeedsContainer)`: типизированно и с понятной ошибкой, если модуль не подключён
  (раньше был словарь `app.state.needs["service"]`, где опечатка в ключе всплыла бы
  только на вызове).
- Меню живёт в `core/access.py` (`MENU`), потому что меню — про права: пункт виден,
  если у роли есть разрешение его модуля. Отдельного меню у модуля нет.
- Тесты собирают приложение с подмножеством модулей: `create_app(config,
  modules=(NEEDS,))` — без monkeypatch четырёх переменных окружения.
- Ядро приложения (`CORE`) объявлено модулем только как владелец схемы: своих
  HTTP-маршрутов у него пока нет (они в `web/app.py`), поэтому `build` и `router`
  не заданы.

**Реализовано на шаге 3.** `create_app` сжался с 308 до 246 строк; в нём осталась
только проводка ядра и два вызова реестра.

## 5. Шов доступа (`core/access.py`)

```python
current_user(request) -> Employee | None      # читает сессию, ходит в people
require(request, permission) -> Employee      # 403, если разрешения нет
ALLOWED: dict[str, frozenset[str]]            # роль -> разрешения (одна таблица)
```

Разрешения (имя = `<модуль>.<действие>`):

| Роль | records | wiki | needs | duty | distribution |
|---|---|---|---|---|---|
| `doctor` (врач) | `view_own`, `edit` | `read` | — | `view_own`, `edit_own` | — |
| `nurse` (медсестра) | `view_own` | — | `view_own`, `edit_own` | — | — |
| `head_nurse` (старшая сестра) | `view_own` | `read` | `view_own`, `edit_own`, `manage`, `catalog` | — | — |
| `head` (заведующий) | `view_own`, `edit` | `read`, `curate`, `settings` | `view_all`, `manage`, `catalog` | `view_all`, `manage` | `manage` |
| `editor` (редактор — врач + куратор) | `view_own`, `edit` | `read`, `curate` | — | `view_own`, `edit_own` | — |

`editor` — это врач с дополнительным правом курирования справочных документов
(ADR-0023). Если редактор в отделении не ходит в ночные смены, право на «Дежурства»
снимается одной строкой таблицы.

Реализовано на шаге 2. Два следствия, которые стоит знать:

- **старшая сестра читает «Компендиум»**, а медсестре он закрыт: `wiki.read` есть
  только у старшей сестры — так было в коде до перестройки, это зафиксировано
  тестом `test_needs_e2e`;
- **`editor` не имеет доступа к «Потребностям»**, хотя прежний код пускал его туда
  на чтение (проверка была «не врач»). Это осознанное сужение по ADR-0023:
  редактор — врач с курированием документов.

Что осталось на потом: шаблоны самих модулей (`needs.html`, `duty.html`) выбирают
UI по `user.role` — это представление, а не контроль доступа; заменим, когда
модули получат свои контейнеры (шаги 3–6).

Раздел в меню появляется по разрешению своего модуля (у «Распределения» — своё,
`distribution.manage`). Заготовка `accrual` (прежний план «Отчёт») **удалена
11.09.2026** по ADR-0024: распределение средств сделано иначе — см.
`docs/ТЗ-распределение.md`.

### Расхождения кода и документации — закрыты 11.09.2026 (ADR-0023)

1. **`editor` сегодня может вводить анестезии.** Подтверждено владельцем как
   правильное: `editor` — это врач с правом курирования документов. В таблице выше
   ему даны права врача (`records`, `duty`) плюс `wiki.curate`.
2. **ADR-5 обещал «заведующий видит всех», код отдаёт только свои записи.**
   ADR-5 в этой части **отменён**: заведующий видит свои анестезии, это норма.
   Обзор поданных анестезий даёт раздел «Распределение» — ADR-0024,
   `docs/ТЗ-распределение.md`.

Оба расхождения закрыты; реализация таблицы — шаг 2 плана.

## 6. Механизм SQLite (`core/db.py`)

```python
open_db(path) -> sqlite3.Connection          # PRAGMA: foreign_keys, WAL, busy_timeout, row_factory
migrate(path, modules) -> list[(module, version)]   # создаёт схему и применяет миграции
SCHEMA_TABLE = "schema_migrations"           # (module, version, applied_at, note)
```

- Каждый модуль объявляет `schema` (CREATE TABLE IF NOT EXISTS …) и `migrations`
  — кортежи `(version, note, [SQL])`. Применённые версии видны в таблице
  `schema_migrations`; `PRAGMA user_version` больше не используется.
- Правило прежнее и остаётся: **опубликованные миграции не редактируются**, только
  добавляются новые.
- `docapp migrate` печатает по одной строке на модуль: `OK: needs version=3`.
  Цепочка `if name == …` удаляется.
- Четыре копии `_connect`/`_apply_migrations` схлопываются в один модуль; хранилища
  получают соединение снаружи.

## 7. Период и статусы (`core/period.py`, `core/statuses.py`)

```python
# period.py
week_of(date) -> date          # понедельник недели
week_range(from_week, to_week) -> ...
shift_date_of(now) -> date|None        # 16:00–09:29 → дата 16:00; 09:30–15:59 → None
shift_window(shift_date) -> (start, end)
label(week_start) -> "10.08.2026 – 16.08.2026"

# statuses.py
DRAFT, SENT, CLOSED = "draft", "sent", "closed"
can(status, action, role) -> bool
apply(status, action) -> str
```

Модуль объявляет свои переходы (у `needs` — `draft/sent` + закрытие недели отдельной
сущностью; у `duty` — `draft/sent/closed`), каркас даёт механику.
Ограничение из ADR-0018: **три функции и таблица констант, без конфигурации процессов
в БД**.

## 8. Схема единой БД

Префикс — владелец. Внешние ключи включены (`PRAGMA foreign_keys = ON`).
Колонки времени — ISO-строки, как сейчас.

### Ядро

| таблица | колонки |
|---|---|
| `employees` | `id PK`, `last_name`, `first_name`, `middle_name`, `role`, `login UNIQUE`, `password_hash`, `buh_id` |
| `anesthesia` | `id PK`, `date`, `patient_name`, `doctor_id → employees`, `nurse_id → employees`, `created_at`, `accrued_at` (NULL = не учтена в распределении) |
| `active_nurse` | `doctor_id PK → employees`, `nurse_id → employees` |

## 9. Перенос данных (`docapp import-legacy`, `docapp check`)

Порядок (сначала на **копии** серверных баз, потом боевой — момент боевого прогона
решается при выкладке, Q6):

1. Копия четырёх БД и `catalog.yaml` в отдельный каталог (никогда не работаем с
   оригиналами; на сервере — существующий `backup.sh`).
2. `docapp migrate --db <новая>` — создаёт схему единой БД.
3. `docapp import-legacy --docapp … --wiki … --needs … --duty … --catalog …` —
   переносит строки с сохранением `id` (иначе поедут ссылки):
   - `employees`, `anesthesia`, `active_nurse` — как есть;
   - `wiki_sources` — BLOB выгружается в `data/wiki/sources/<id>-<обезличенное имя>`;
   - `requests` v1 → `needs_requests`: `category` выводится по строкам
     (есть строка `grp='Растворы'` → `solutions`, иначе `medicaments`) — то же правило,
     что в миграции v2, только применяется сразу к новой схеме;
   - `closure` → две строки в `needs_closures` (по одному разделу на каждую);
   - `catalog.yaml` → `needs_catalog_*`; первая запись журнала — `action='import'`;
   - `duty_report/duty_operation` → `duty_reports/duty_operations`.
4. **Идемпотентность:** повторный прогон не дублирует строки (проверка по `id` и по
   `UNIQUE`-ключам), поэтому перенос можно перезапускать без страха.
5. `docapp check` — отчёт: счётчики «до/после» по таблицам, сироты
   (`author_id`/`doctor_id`/`closed_by` без `employees`), строки заявок без заявки,
   расхождение сумм.

Критерий приёмки шага: счётчики совпадают, сирот нет, приложение поднимается на
перенесённой БД и сценарные тесты зелёные.

## 10. Ключевые потоки (проверка механики)

### 10.1 Закрытие недели «Потребностей» (раздел «Растворы», база «Ленская»)

1. `POST /needs/api/close` → `{base: "Ленская", category: "solutions", week: "2026-08-10"}`.
2. `core.access.require(needs.manage)` → старшая сестра или заведующий, иначе 403.
3. `core.period.week_of(...)` — если неделя не передана.
4. `NeedsService.close`: собрать отправленные точки раздела
   (`needs_requests where status='sent'`), вычислить неотправленные из каталога.
5. `needs_closures` — `INSERT OR REPLACE` по `(base, week_start, category)`.
6. Ответ: `{"closed": true, "unsent_points": [...]}`. **Неотправленные точки не
   блокируют закрытие** — они предупреждение, а не ошибка.
7. После закрытия правки и отправка этой базы и **этого раздела** — 409 (NeedsClosed);
   медикаменты той же базы остаются открытыми.

### 10.2 Отчёт дежурства: черновик → отправка → закрытие

1. Врач, окно смены: `core.period.shift_date_of(now)` → дата 16:00; вне окна — 409.
2. `POST /duty/api/report` — сохраняет черновик (`status='draft'`), операции
   заменяются целиком (`DELETE` + `INSERT` с `position`).
3. `POST /duty/api/send` → `draft → sent`. Отправленный отчёт **остаётся правимым**:
   `save` для `sent` разрешён, `core.statuses.can(sent, edit, role)` → true.
4. Заведующий: `POST /duty/api/close` (один отчёт) или `close-shift` (вся смена) →
   `→ closed`. Переоткрытие: `closed → sent`.
5. Ленивое авто-закрытие: при первом чтении доски/выгрузки `duty.manage`-роут
   закрывает отчёты, чьё окно смены уже прошло (планировщика на хостинге нет).
6. В выгрузку `.xlsx` попадают только `closed` — правило сохраняется.

### 10.3 «Распределение» — проверка каркаса

> Переименование: шаг 7 сделал модуль `summary` («Сводка»); 11.09.2026 он стал
> разделом «Распределение» — пакет `distribution`, своё разрешение
> `distribution.manage` только у заведующего (ADR-0024, шаг 2
> `docs/ТЗ-распределение.md`). Ниже — в формулировках того времени.

1. ✅ Новый модуль `summary` (ныне `distribution`): **без своей схемы**, пункт
   меню в `core/access.MENU`; на шаге 7 видимость шла от прав на записи, теперь
   это раздел заведующего.
2. ✅ Роутер `GET /distribution/api/aggregate?from=…&to=…&by=…` →
   `core.access.require(distribution.manage)` — только заведующий.
3. ✅ Сервис `distribution` берёт интерфейс `records` и справочник `people` из
   `context.containers` (соседи объявлены раньше в реестре) и вызывает
   `AnesthesiaService.aggregate(...)` — таблицу `anesthesia` не читает.
4. ✅ Интерфейс `records` объявлен как `Protocol` **у потребителя**
   (`distribution/service.RecordsInterface`): модулю важно, что записи можно
   посчитать за период, а не то, какой у них класс. Проверяется подстановкой
   заглушки.
5. Отклонение от этой записи: разреза `base` нет — у анестезии нет базы, есть
   врач, сестра, месяц и день. Вместо выдуманного разреза сделаны четыре честных:
   `doctor`, `nurse`, `month`, `day`. Если появится деление по базам, его сначала
   надо завести в записях, а не в сводке.

### 10.4 Правка каталога расходки старшей сестрой

1. `POST /needs/api/catalog/item` → `core.access.require(needs.catalog)`.
2. `NeedsService.catalog_upsert(...)` — `INSERT OR REPLACE` в `needs_catalog_items`
   + строка в `needs_catalog_audit` (кто/когда/что) в одной транзакции.
3. Особую группу «Растворы» переименовывать нельзя — проверка в сервисе.
4. `GET /needs/api/catalog/export` — выгрузка текущего каталога в YAML
   (резервная копия глазами). Импорт YAML — только команда CLI, в UI не выставляем.

## 14. Что решаем при выкладке на сервер (отложено, Q6/Q9)

1. `duty.db` не попадает в `backup.sh`/`restore.sh` — сейчас отчёты дежурств без бэкапа.
2. `.env` на сервере содержит `CONSULT_*`, а нужны `AI_API_KEY`, `WIKI_DB`, `DUTY_DB`
   (после перестройки — одна `DOCAPP_DB` и папка источников).
3. `data/consult/` — 21 МБ PDF с ФИО пациента в имени + 14 диалогов, код про них не знает.
4. На сервере расходятся два пути деплоя: `.git` застрял на `bcb1bb4`, `REVISION` —
   `10c9923`; надо оставить один.
5. `catalog.yaml` под `.gitignore` — после ADR-0019 каталог живёт в БД, и это перестаёт
   быть проблемой; до выкладки — кладём seed в git (ПДн в нём нет).
6. Бэкап станет двухчастным: БД + папка PDF-источников (ADR-0020).

## 15. Риски и принятые слабые места

1. **Изоляция модулей становится логической, а не файловой.** Сбой в одном модуле
   виден всем. Компенсация: транзакции, один реестр миграций, бэкап перед выкладкой.
2. **Шаг 4 (слияние БД) необратим без обратного скрипта.** Обратный перенос из одной
   БД в четыре не пишем: старые БД остаются нетронутыми до подтверждения.
3. **Четыре шага подряд меняют каркас при работающем приложении.** Смягчение: каждый
   шаг отдельный коммит, сценарные тесты зелёные, остановиться можно после любого.
4. **Каталог в БД (шаг 6)** теряет возможность править расходку файлом «на ходу» в
   проводнике. Компенсация: экспорт в YAML и команда импорта.
5. **Журнал каталога** отвечает на вопрос «кто менял», но не делает правки отменяемыми.
6. **Модуль распределения (`summary`, ныне `distribution`) может не поместиться в каркас** — это и есть проверка: если
   придётся читать `anesthesia` напрямую, правим каркас, а не обходим его.
