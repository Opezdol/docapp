# ТЗ v1.0: Разделение «Потребностей» на растворы и медикаменты

> **Статус: реализовано (T1–T9).** Все развилки закрыты; §1 и §6 фиксируют решения.
> **For Hermes:** реализация субагентами (isolated-subapp-subagents), по одной
> задаче с двухэтапной проверкой и коммитом; полный pytest зелёный после каждой
> интеграционной задачи.

**Цель:** в разделе «Потребности» логически разделить сбор заявок с точек
пополнения на два раздела — **растворы** и **медикаменты** — с раздельной
отправкой, раздельным закрытием недель и раздельными отчётами. Граница раздела
выводится из каталога без его перестройки.

**Главный принцип:** не сломать работающее. Существующие 322 теста остаются
зелёными; правки существующего кода — только внутри пакета `src/docapp/needs/`
и его тестов (§2). Основная `docapp.db` и другие разделы не затрагиваются.

---

## 1. Решения (зафиксированы в обсуждении)

1. **Жизненный цикл — раздельный.** У растворов и медикаментов свои кнопки
   «Отправить», свой статус (`draft`/`sent`), независимые закрытие и отчёты.
2. **Граница раздела — из каталога, без перестройки файла.** Группа «Растворы»
   = раздел «растворы»; все остальные группы = раздел «медикаменты».
3. **Доска старшей — две секции.** «Растворы» и «Медикаменты», у каждой своя
   сетка точек с баз.
4. **Аналитика — фильтр «Раздел»** (растворы / медикаменты / все) к текущим
   фильтрам.
5. **Форма сестры — два отдельных поиска** (по одному в каждой секции) и две
   секции с независимыми «Сохранить»/«Отправить».
6. **Коллоиды → «Растворы».** Группа «Парентеральное» удалена; Гелофузин и
   Геласпан перенесены в группу «Растворы» (итого 8 позиций).
7. **Группа «Медикаменты» не переименовывается** — одноимённость с разделом
   «медикаменты» принята.
8. **Аналитика «Все»** — растворы и медикаменты выводятся двумя отдельными
   блоками (сначала «Растворы» поточково, затем «Медикаменты» по группам).

## 3. Модель данных

### Разделы (константы в `catalog.py`)

```python
CATEGORY_SOLUTIONS   = "solutions"     # группа «Растворы»
CATEGORY_MEDICAMENTS = "medicaments"   # все остальные группы
CATEGORY_LABELS = {
    CATEGORY_SOLUTIONS: "Растворы",
    CATEGORY_MEDICAMENTS: "Медикаменты",
}

def category_of(grp: str) -> str:
    return CATEGORY_SOLUTIONS if grp == SOLUTIONS_GROUP else CATEGORY_MEDICAMENTS
```

Внутренние значения — английские (`solutions`/`medicaments`), хранятся в БД и
API; подписи — русские («Растворы»/«Медикаменты»). Снимок строки (`grp`)
остаётся русским названием группы; раздел строки выводится из `grp`.

### Схема БД (v2)

```sql
CREATE TABLE requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    base TEXT NOT NULL,
    point TEXT NOT NULL,
    week_start TEXT NOT NULL,
    category TEXT NOT NULL,              -- 'solutions' | 'medicaments'
    author_id INTEGER NOT NULL,
    status TEXT NOT NULL DEFAULT 'draft',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (base, point, week_start, category)
);
-- request_lines БЕЗ изменений: категория строки выводится из снимка grp
CREATE TABLE closures (
    base TEXT NOT NULL,
    week_start TEXT NOT NULL,
    category TEXT NOT NULL,
    closed_at TEXT NOT NULL,
    closed_by INTEGER NOT NULL,
    PRIMARY KEY (base, week_start, category)
);
```

Точка за неделю имеет **до двух заявок** — по одной на раздел. Строки растворов
хранят `grp='Растворы'`; строки медикаментов — любую другую группу.

### Миграция (SCHEMA_VERSION 1 → 2)

Пересборка `requests` и `closures` с новой колонкой (SQLite не меняет UNIQUE через
`ALTER`, прецедент — пересборка таблицы anesthesia). Сейчас `data/needs/needs.db`
пуст (0 строк) — потери нет. Миграция при этом сохраняет любые существующие
строки: смешанные заявки разводятся по разделам (растворы-строки →
`solutions`, медикаменты-строки → `medicaments`), старые закрытия дублируются
на оба раздела (сохраняется «закрыто»).

## 4. Функциональные требования

### Форма сестры

- **F1.** Форма точки делится на две секции — «Растворы» и «Медикаменты»,
  переключаемые вкладками. Сетка «Точки пополнения» помечает точки цветом по
  активной вкладке: жёлтый — черновик, зелёный — отправлена, серый — нет
  заявки (с точки зрения медсестры: чужой черновик — серый).
- **F2.** В каждой секции — свой поиск по каталогу (растворы-поиск фильтрует
  только группу «Растворы», медикаменты-поиск — остальные группы), своя таблица
  позиций (количество — поле со степпером «−/+»), свои кнопки «Сохранить»
  и «Отправить».
- **F3.** Сохранение/отправка одного раздела не затрагивает другой раздел той же
  точки (два независимых запроса `(base, point, week, category)`).
- **F4.** Правила правок и просмотра — как раньше (своя/чужая/закрытая), но на
  уровне раздела: закрытый раздел делает свои строки read-only, другой раздел
  остаётся редактируемым. Медсестра видит закрытие раздела сразу: эндпоинт
  `GET /needs/api/closed` (доступен nurse+) отдаёт закрытые `{base, category}`
  за неделю; сетка точек показывает бейдж «раздел закрыт», секция формы — read-only.

### Доска старшей

- **F5.** Доска старшей — три вкладки: «Растворы», «Медикаменты», «Аналитика».
  В первых двух — своя сетка точек обеих баз со статусом (нет заявки/черновик/
  отправлено), автором и признаком закрытия раздела; вкладка «Аналитика» —
  фильтры и свод инлайн (та же форма, что на странице `/needs/analytics`).
- **F6.** Клик по точке секции открывает форму этой точки в соответствующем
  разделе.

### Закрытие недели

- **F7.** По базе — две пары кнопок: «Закрыть растворы …»/«Открыть заново» и
  «Закрыть медикаменты …»/«Открыть заново». Закрытие раздела не затрагивает
  другой раздел той же базы.
- **F8.** Закрытие раздела фиксирует `closures(base, week, category)`, запрещает
  правку/отправку строк этого раздела и возвращает предупреждение о неотправивших
  точках (по разделу).

### Отчёты

- **F9.** По базе — две пары кнопок: «Растворы (xlsx / просмотр)» и
  «Медикаменты (xlsx / просмотр)». Каждый отчёт строится строго по своему
  разделу за неделю.
- **F10.** Растворы-отчёт — поточковый лист «Раствор | Ед. | <точки> | ИТОГО»
  (как текущий лист «Растворы»). Медикаменты-отчёт — секции по группам с
  подытогами (как текущий лист «Потребность»).

### Аналитика

- **F11.** Добавить фильтр «Раздел» (растворы / медикаменты / все). «Растворы» →
  только поточковый свод; «Медикаменты» → только свод по группам; «Все» →
  оба раздела двумя отдельными блоками (сначала «Растворы» поточково, затем
  «Медикаменты» по группам). Экспорт `.xlsx` учитывает фильтр.

### Общее

- **F12.** PWA-вёрстка адаптивная, без CDN, русский язык (как раньше).
- **F13.** Роли без изменений: медсестра — форма (обе секции); старшая/зав —
  доска, закрытие, отчёты, аналитика; врач — 403.

## 5. План задач (субагенты)

- **T1. Каталог** (`catalog.py`): константы `CATEGORY_SOLUTIONS`/`CATEGORY_MEDICAMENTS`,
  `CATEGORY_LABELS`, `category_of(grp)`; тесты `test_needs_catalog.py`.
- **T2. Хранилище** (`store.py`): схема v2 (колонка `category` в `requests`/
  `closures`, новые UNIQUE/PK), миграция 1→2, CRUD с `category`,
  `list_requests(base, category, week)`; тесты `test_needs_store.py`.
- **T3. Сервис** (`service.py`): category-aware `save/submit/get_for_user/board/
  close/reopen/is_closed`; валидация строк раздела (растворы-заявка принимает
  только растворы, и наоборот); тесты `test_needs_service.py`.
- **T4. Отчёт** (`report.py`): `aggregate_requests(..., category)`,
  `build_xlsx(agg)` / `html_table(agg)` — отчёт одного раздела; тесты
  `test_needs_report.py`.
- **T5. Аналитика** (`analytics.py`): параметр «раздел» в `summarize` (solutions/
  medicaments/None), фильтр по разделу; тесты `test_needs_analytics.py`.
- **T6. Роутер** (`router.py`): `category`/`section` во всех endpoint'ах (request,
  submit, board, close/reopen, report, analytics); API-тесты `test_needs_api.py`.
- **T7. UI сестры** (`needs.html/js/css`): две секции формы с двумя поисками и
  независимыми «Сохранить»/«Отправить».
- **T8. UI старшей** (`needs.html/js/css`, `analytics.html`): доска двумя
  секциями, раздельные закрытие/отчёты по базе, фильтр «Раздел» в аналитике.
- **T9. E2E + документация**: сквозной тест «растворы и медикаменты независимы»
  (отправка/закрытие/отчёт одного раздела не трогает другой), полный pytest
  (322 + новые), живой смоук uvicorn; ADR-12 в README + актуализация раздела
  «Потребности».

Порядок: T1→T2→T3→T4→T5 (слои снизу вверх), затем T6 (роутер), затем T7→T8
(UI), T9 — после интеграции. Каждая задача — полный зелёный pytest и коммит.

## 7. Риски

| Риск | Митигация |
|---|---|
| Сломать существующие тесты | Правки только в `needs/`; полный pytest после каждой задачи |
| Миграция схемы | Пересборка таблиц (прецедент anesthesia); БД пуста — без потери; тест миграции с данными |
