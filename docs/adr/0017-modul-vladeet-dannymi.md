# ADR-0017. Модуль владеет данными; роутер — только HTTP-адаптер

- **Статус:** принято, реализовано (шаги 1–3, 7; 11.09.2026)
- **Дата:** 2026-09-11
- **Контекст:** Роутеры `needs`, `duty`, `wiki` импортировали `docapp.web.app`
  ради `current_user`. Двух вещей это стоило: круговой импорт (роутеры пришлось
  подключать лениво внутри `create_app`, а вместе с ними туда переехали конфиги,
  создание БД и сборка сервисов) и смешение слоёв — в `needs/router.py` живёт сборка
  отчёта, в `duty/router.py` — группировка выгрузки, в `wiki/router.py` — запуск OCR
  в потоке. Плюс три подприложения читали `app.state.employees` напрямую в цикле.

- **Решение:**
  1. У каждых данных ровно один модуль-владелец. Правила живут только там.
  2. Роутер не владеет данными и не хранит правил: он переводит HTTP в вызовы
     интерфейса модуля.
  3. Пересечение шва — только через интерфейс. Появляется модуль `people`
     (владелец сотрудников), его интерфейс — `People`; прямой доступ к таблице
     `employees` из других модулей запрещён.
  4. Появляется модуль `core.access` — шов «кто пользователь и что ему можно».
     Роутеры больше не импортируют `web.app`; `create_app` подключает их обычным
     `include_router` на уровне модуля.
  5. Порты-ABC в `storage/store.py` (по одному адаптеру на каждый) удаляются как
     гипотетический шов: второй реализации нет, а тесты и так используют настоящий
     SQLite во временном файле.

- **Как сделано (шаг 7):**
  - `storage/` исчез: движок — в `core/db.py`, сотрудники — в `people/store.py`,
    записи анестезий и «активная сестра» — в `records/store.py`; версия схемы
    ведётся на модуль (было одно `docapp` — стало `people` v1 и `records` v3 с
    прежними миграциями);
  - `records` стал полноценным модулем: `container.py` + `module.py` +
    `router.py` (главная страница, ввод/правка/удаление записи, выбор сестры) и
    свои шаблоны; `web/app.py` из 248 строк стал тонкой сборкой (~140) и держит
    только вход, «Мои данные», обработчики ошибок и статику;
  - интерфейс для соседей — **между контейнерами**: `AppContext.containers`
    наполняется по ходу сборки, поэтому модуль видит интерфейсы соседей,
    объявленных в реестре раньше. `summary` (последний в реестре) берёт
    `RecordsContainer` и `PeopleContainer` и не имеет своей схемы вовсе;
  - интерфейс объявляет **потребитель**, а не владелец:
    `summary/service.RecordsInterface` (`Protocol` с `aggregate`), поэтому сводка
    проверяется подстановкой чужого объекта-заглушки, а не только настоящим
    сервисом;
  - справочник сотрудников берут через контейнер `people`
    (`container_of(request, "people", PeopleContainer)`) — прежнее чтение
    `app.state.employees` из роутеров убрано. Одно исключение — сам `web/app.py`:
    у приложения есть шов доступа (`core.access.current_user`) и вход, которые
    нужны всегда, даже когда модуль `people` не подключён (тесты собирают
    подмножество модулей).

- **Последствия:**
  - пересматривает **ADR-9** в части «роутеры подключаются лениво — иначе круговой импорт»;
  - `create_app` становится тонкой сборкой, а не источником правды о модулях;
  - убирает N+1 обращения к сотрудникам на доске старшей и в аналитике «Компендиума»;
  - новый модуль, которому нужны анестезии (например «Сводка»), не читает таблицу
    `anesthesia`, а вызывает `records` — это и есть проверка каркаса;
  - порядок в `MODULES` стал значимым: модуль может взять интерфейс только у того,
    кто объявлен раньше. Новый модуль-потребитель добавляется **после** своих
    поставщиков, иначе сборка падает с внятной ошибкой, а не молча читает пустоту.
