# ADR-0026. Форма таблиц сверяется с объявлением, остатки прежней схемы лечит repair-schema

- **Статус:** принято, реализовано 2026-09-11
- **Дата:** 2026-09-11
- **Контекст:** при работе с приложением добавление анестезии упало:
  `sqlite3.IntegrityError: NOT NULL constraint failed: anesthesia.history_number`.
  Причина не в коде записи, а в файле: `data/docapp.db` достался от прежней базы,
  где у `anesthesia` была обязательная колонка `history_number` (её убрала
  миграция v2 — минимизация данных, ADR-14). Файл «усыновили», версию модуля
  записали текущей, а форму таблицы никто не сверял: `CREATE TABLE IF NOT EXISTS`
  таблицу **другой формы** принимает молча и ничего не пересоздаёт. Итог: 588
  зелёных тестов и падение на первой же записи — тестовая БД каждый раз
  собирается с нуля и потому всегда имеет текущую форму.
- **Решение:**
  - движок (`core/db.py`) умеет **читать объявление таблиц из DDL модуля**
    (`declared_tables`) и сверять с файлом (`shape_problems`): объявление —
    источник правды (ADR-0016), всё, чего в нём нет, — остаток прежней схемы;
  - `ensure_schema` проверяет форму при каждом открытии и **пишет
    предупреждение** в лог (`Схема records: таблица anesthesia содержит лишние
    колонки (history_number) — она осталась от прежней схемы, запись в неё
    упадёт`), но открытие не срывает: читать такую базу можно, и отказ в старте
    приложения в разгар смены был бы хуже понятного предупреждения;
  - `docapp check` показывает то же расхождение как замечание и возвращает
    ненулевой код — это ловит дефект до того, как пользователь нажмёт
    «Сохранить», и до выкладки;
  - лечит **`docapp repair-schema`**: пересобирает таблицу ровно по объявлению
    (CREATE → INSERT по общим колонкам → DROP → RENAME), лишние колонки
    убираются, строки сохраняются. Функция `core.db.repair` делает то же для
    списка схем — её вызывают CLI и тесты.
- **Последствия:**
  - файл, оставшийся от прежней схемы, больше не «работает до первой записи»:
    о расхождении известно из лога и из `check`;
  - данные в лишних колонках не сохраняются — это и есть намерение (ADR-14);
    колонки, которых нет в объявлении, считаются мусором прежней схемы;
  - перенос данных через `docapp import-legacy` даёт файл правильной формы
    (проверено на репетиции: `anesthesia` без `history_number`), поэтому штатный
    путь выкладки не требует `repair-schema`; команда нужна для файлов,
    усыновлённых напрямую;
  - **побочный эффект упавшей записи:** после `IntegrityError` соединение
    остаётся с открытой транзакцией и держит блокировку записи — приложение
    начинает отвечать `database is locked` на любую запись, пока процесс не
    перезапустят. Перезапуск dev-сервера — часть лечения, а не отдельная
    случайность.
